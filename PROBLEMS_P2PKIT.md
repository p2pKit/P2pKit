# P2pKit — Production-Readiness Audit: Problems & Fixes

> **Project:** P2pKit — a Kotlin Multiplatform peer-to-peer local-network library connecting Android, iOS, Windows, macOS, and Linux.
> **Audit date:** 2026-05-29  
> **Scope:** Exhaustive line-by-line review of every module (core, LAN transport, provisioning, samples, build/publish config, tests).  
> **Goal:** Take the project from MVP to production-grade, publishable.

## How this audit was produced

Every source file was read line-by-line by a dedicated reviewer (one per module), and **every finding was then independently re-verified against the real code by a separate adversarial verifier** that confirmed, adjusted, or rejected it. All reviewing/verifying agents ran on Opus 4.8. Findings that could not be substantiated against the actual code were dropped (see *Appendix: Rejected findings*). Counts below reflect only **confirmed + adjusted** findings.

### Top blockers to publishing (fix these first)

1. **The library cannot be published at all** — no `maven-publish`/`signing` plugin, no `group`/`version`, no POM metadata, no `LICENSE` file on any module. (`no-publishing-plugin`, `no-pom-metadata`, `no-publishing-config`, `no-license-file`)
2. **Unauthenticated remote DoS** — inbound frame payload length is trusted up to ~2 GiB with no cap; a peer can force OOM. The reassembler has no aggregate cap and its stale-eviction is dead code. (`frame-reader-unbounded-payload-dos`, `unbounded-frame-payload-dos`, `reassembler-no-aggregate-size-cap`, `reassembler-evictstale-never-called`)
3. **Native resource leak** — Android `LocalOnlyHotspot`/Wi-Fi-join reservations are never released on `kit.stop()`. (`hotspot-not-released-on-kit-stop`)
4. **Public lifecycle contract is wrong** — documented `P2pState` transitions don't match what the kit emits; `stop()` permanently kills the instance while reporting success on restart. (`state-lifecycle-contract-violated`, `kit-single-use-after-stop`)
5. **Identity not verified on outgoing connect** — a LAN device racing the expected host:port is accepted under the intended peer's id. (`outgoing-peer-id-not-verified`)

## ✅ Fixes applied in this pass

All fixes below were implemented and **verified green** against:
`./gradlew :p2p-core:compileTestKotlinJvm :p2p-transport-lan:compileTestKotlinJvm` (compiles),
`:p2p-core:jvmTest` (**134 tests, 0 failures**), and `:p2p-network-provisioning-android:testAndroidHostTest` (**15 tests, 0 failures**).

**Security / DoS (critical & high):**
- `frame-reader-unbounded-payload-dos`, `unbounded-frame-payload-dos` — added `ProtocolConstants.MAX_FRAME_PAYLOAD_BYTES` (8 MiB) and enforce it in `FrameReader.feed` (before buffering) and `FrameCodec.decode`; `frameSize` now uses `Long` arithmetic to avoid Int overflow.
- `reassembler-no-aggregate-size-cap`, `reassembler-totalsize-int-overflow` — `Reassembler` now tracks per-message buffered bytes as `Long`, rejects a message that would exceed `MAX_PAYLOAD_BYTES`, caps `totalChunks` (`MAX_TOTAL_CHUNKS`) and the concurrent-pending count (`MAX_PENDING_REASSEMBLIES`).
- `reassembler-evictstale-never-called` — `evictStale()` is now driven from `DefaultP2pProtocol.events()` on each inbound batch (was dead code).
- `malformed-control-payload-tears-down-session` — HELLO/FILE_OFFER JSON decode wrapped; a malformed control frame is skipped + warned instead of throwing into `routeEvents` (closes the reconnect-loop vector).
- `hello-fileoffer-no-field-validation`, `untrusted-filename-no-validation`, `offer-size-mismatch-not-checked` — `HelloPayload.decode`/`FileOfferPayload.decode` now bound string fields and reject negative `sizeBytes`.
- `outgoing-peer-id-not-verified` — outgoing handshake now verifies the remote's HELLO `peerId` matches the dialed peer; mismatch sends ERROR + throws `HandshakeRejected`. (Test fixtures updated to seed matching ids, mirroring production discovery.)

**Lifecycle correctness (high):**
- `state-lifecycle-contract-violated` — `ensureStarted()` now drives `Starting → Running`, and emits `Failed(TransportStartFailed)` on bind failure; `Running` is reached by `start()`, not only `startAdvertising()`.
- `kit-single-use-after-stop`, `stop-not-restartable-contract-mismatch` — `stop()` sets a terminal `stopped` flag; subsequent lifecycle calls throw `IllegalStateException` instead of silently no-op'ing onto a dead scope. `States.kt` KDoc corrected (Stopped is terminal).
- `notify-backgrounded-state-and-transport-mismatch`, `background-state-stopped-not-restartable`, `background-double-close` — backgrounding no longer emits a misleading `Stopped` while transports stay bound, and no longer double-closes sessions.
- `startadvertising-state-overwrite-failed` — `startAdvertising()` wrapped so a partial failure surfaces as `Failed`.
- `hotspot-not-released-on-kit-stop` — `AndroidNetworkProvisioningManager` now releases the `LocalOnlyHotspot` reservation and joined-network binding via `scopeJob.invokeOnCompletion { … }` (fields made `@Volatile`), so `P2pKit.stop()` actually frees them.

**File transfer (high):**
- `reconnect-rewrites-midstream` — `rearmWith` fails all in-flight transfers (`closeAll`) before swapping the connection, so a mid-stream sender can't write onto the new epoch.
- `ondata-failure-uncaught-nonp2p` — `onFileData` now catches `Throwable` (rethrowing cancellation), aborts the receiver, and scopes the failure to the one transfer instead of tearing down the session.

**Concurrency / robustness (medium/low):**
- `manual-peer-ids-unsynchronized`, `manual-peer-id-set-unsynchronized-vs-stateflow`, `manual-peer-ids-never-cleaned` — folded the manual flag into `TrackedPeer` and removed the unsynchronized `MutableSet` (eliminates the data race + the separate growth).
- `evict-loop-no-error-isolation` — per-iteration try/catch keeps the eviction loop alive.
- `transport-tie-break-nondeterministic` — `selectBestTransport` now breaks priority ties deterministically.
- `assert-invariants-const-true-in-prod` — `SessionStore` invariant violations now **log** instead of crashing the host process.
- `reassembler-toString-string-template-bug` — fixed the broken `$frame.totalChunks` interpolation.
- `unused-runblocking-import` — removed.

**Build / publish (critical, partial):**
- `no-license-file` — added a top-level Apache-2.0 `LICENSE` *(default choice — change to MIT etc. if you prefer)*.
- `no-publishing-plugin`, `no-pom-metadata` — added `GROUP=dev.p2pkit` / `VERSION_NAME=0.6.0` coordinates (single source of truth) and wired `group`/`version` onto every module. **Remaining (documented, not applied):** the `maven-publish`/`com.vanniktech.maven.publish` plugin + POM + signing wiring — left to a CI step because it cannot be validated here without signing keys and a full multiplatform (incl. iOS/konan) publish dry-run.

### Documented but intentionally not applied here
- **Anything requiring the full iOS/Android multiplatform toolchain or real devices to validate** (most `p2p-transport-lan` Apple/Android findings, `needsHardware` items) — fixes are specified above for a device/CI pass.
- `blocking-sink-write-on-route-loop` — the correct fix (per-transfer bounded-channel writer) is a larger rework needing its own tests; specified above.
- `frame-header-version-not-validated` — deliberately **not** hard-rejected at the codec to preserve graceful version negotiation in the HELLO handshake (a strict frame-version reject would convert a future peer's `VersionMismatch` into a `ProtocolError`).
- The long tail of low-severity docs/dead-code/test-quality items — each has a concrete proposed fix in its entry below.

## 🔴 Critical findings

#### 🔴 `no-pom-metadata` — No POM metadata (name/description/url/licenses/developers/scm) — fails Maven Central validation
- **File:** `build.gradle.kts:1-9`
- **Category:** build · **Fix validation:** ✅ no hardware needed
- **Problem:** Confirmed as a direct consequence of no-publishing-plugin: with no publishing plugin and no `pom {}` block anywhere (grep for licenses/developers/scm returns nothing), no generated POM exists, so none can carry the name/description/url/license/developer/scm fields Sonatype Central Portal requires. Note this is effectively the same root cause as no-publishing-plugin rather than a fully independent defect, but the POM-field requirement is a distinct Central validation gate worth tracking.
- **Impact:** Even after adding maven-publish, the Central upload is rejected at validation for missing required POM fields. Blocks publication.
- **Fix:** In the publishing convention, populate the full POM: name, description, url, licenses { license { name; url } } (matching the added LICENSE file), developers { developer { id; name } }, and scm { url; connection; developerConnection }.

#### 🔴 `no-publishing-plugin` — Library is not publishable: no maven-publish/signing plugin, no group, no version on any module
- **File:** `p2p-core/build.gradle.kts:1-108`
- **Category:** build · **Fix validation:** ✅ no hardware needed
- **Problem:** Verified by reading every build file. Root build.gradle.kts only applies plugins with `apply false`. No module (p2p-core, p2p-transport-lan, p2p-network-provisioning-android/-desktop) applies maven-publish, signing, or com.vanniktech.maven.publish. gradle.properties contains only kotlin/gradle/android flags — no group, no VERSION_NAME. libs.versions.toml has no group/version coordinates. A repo-wide grep for `maven-publish|signing|mavenPublish|com.vanniktech|publishing|developers|licenses|scm` over all *.kts/*.toml/*.properties returned zero hits. The KMP and Android-KMP-library plugins do not auto-create publications, so there are no publish* tasks at all.
- **Impact:** The library cannot produce a single Maven artifact. Consumers can only use it via includeBuild/project dependency, never `implementation("dev.p2pkit:p2p-core:0.x")`. This is the single biggest blocker to the stated goal of a publishable SDK.
- **Fix:** Apply a publishing convention (recommended com.vanniktech.maven.publish for KMP + Android multiplatform publications) in each library module; set group="dev.p2pkit" and a single source-of-truth version (e.g. gradle.properties VERSION_NAME). Configure coordinates + pom + signAllPublications(). Exclude sample/iosApp modules.

#### 🔴 `frame-reader-unbounded-payload-dos` — FrameReader trusts attacker-controlled payload length with no upper bound (memory-exhaustion DoS)
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/protocol/FrameReader.kt:47-54`
- **Category:** security · **Fix validation:** ✅ no hardware needed
- **Problem:** FrameReader.feed() reads payloadLen = FrameCodec.readIntBE(buffer, 32) and only rejects payloadLen < 0 (line 50). It then computes frameSize = HEADER_SIZE + payloadLen and waits until buffer.size >= frameSize, buffering every inbound chunk into an ever-growing ByteArray, then allocates buffer.copyOfRange(0, frameSize). payloadLen is a peer-controlled 32-bit big-endian value up to ~2 GiB. ProtocolConstants.MAX_PAYLOAD_BYTES (4 MiB) is enforced ONLY outbound in Chunker.chunk() (Chunker.kt:33); a workspace grep confirms it has no inbound enforcement point. FrameCodec.decode() also only rejects negative payloadLen (FrameCodec.kt:82-84), not an upper bound.
- **Impact:** Any peer on the LAN (no auth under NoneForMvp) can drive a P2pKit process to OOM by sending a 36-byte header declaring a huge payload followed by a slow byte stream. On constrained Android/iOS devices this kills the app. Remote, trivially triggerable denial-of-service.
- **Fix:** Add a MAX_FRAME_PAYLOAD_BYTES constant to ProtocolConstants (e.g. MAX_PAYLOAD_BYTES plus a small header/JSON allowance, or a dedicated larger cap sized for FILE_DATA chunks) and enforce it in FrameReader.feed() immediately after reading payloadLen: throw P2pError.ProtocolError when payloadLen exceeds it (this closes the session). Mirror the same check in FrameCodec.decode(). Unit-testable without hardware.

#### 🔴 `no-inbound-payload-length-cap-test` — No test for untrusted oversized payload-length header (unbounded-allocation DoS)
- **File:** `p2p-core/src/commonTest/kotlin/dev/p2pkit/core/protocol/FrameCodecTest.kt:138-145`
- **Category:** security · **Fix validation:** ✅ no hardware needed
- **Problem:** Confirmed against the real code. FrameCodec.decode (FrameCodec.kt:82-90) validates payloadLen<0, totalChunks<=0, chunkIndex range, and truncation, but never enforces an upper bound against ProtocolConstants.MAX_PAYLOAD_BYTES (4 MiB). FrameReader.feed (FrameReader.kt:49-54) reads payloadLen, rejects only <0, then computes frameSize = HEADER_SIZE + payloadLen and keeps buffering (growing the combined ByteArray at lines 40-43) until it has that many bytes. MAX_PAYLOAD_BYTES is referenced ONLY by Chunker (Chunker.kt:16,20) on the outbound path; grep confirms no decode-side enforcement. FrameCodecTest only has decodeRejectsNegativePayloadLength (138-145) and decodeRejectsTruncatedPayload; there is no test feeding a large positive payloadLen, and FrameReaderTest has no oversized-length test.
- **Impact:** Under NoneForMvp (no auth), any LAN peer can send a 36-byte header with a payload-length near Int.MAX and force a ~2 GiB allocation / unbounded buffering, OOM-killing the process. No test guards the cap's presence. Real DoS vector on a publishable library.
- **Fix:** Enforce payloadLen > ProtocolConstants.MAX_PAYLOAD_BYTES in BOTH FrameCodec.decode and FrameReader.feed (reject before buffering/allocating) with P2pError.ProtocolError. Add (a) FrameCodecTest.decodeRejectsPayloadLengthOverMax overwriting offset 32 with a value > MAX_PAYLOAD_BYTES; (b) a FrameReaderTest that feeds only an oversized header and asserts feed() throws and bufferedBytes() stays bounded.

#### 🔴 `hotspot-not-released-on-kit-stop` — LocalOnlyHotspot reservation and Wi-Fi join are never released when the kit stops
- **File:** `p2p-network-provisioning-android/src/androidMain/kotlin/dev/p2pkit/provisioning/android/AndroidNetworkProvisioningManager.kt:59-60, 236-242`
- **Category:** resource-leak · **Fix validation:** ✅ no hardware needed
- **Problem:** Verified against the real code. The manager attaches its scope to the kit's parent job (AndroidNetworkProvisioningManager.kt:59 `SupervisorJob(parent = ctx.parentJob)`, where parentJob = internalJob, P2pKitImpl.kt:200). P2pKitImpl.stop() (lines 352-363) only calls `internalJob.cancel()` (line 361) and never calls `networkProvisioning.close()` — confirmed by grep: no caller of provisioning close() exists anywhere in p2p-core. The actual native release (`reservation.close()` via handle.close(), and `bindProcessToNetwork(null)` via joinHandle.close()) lives ONLY in AndroidNetworkProvisioningManager.close() (lines 236-242). There is NO `scopeJob.invokeOnCompletion { ... }` in the module (grep confirms zero invokeOnCompletion in either provisioning module). Cancelling internalJob cancels scopeJob → tears down the stopWatch/joinReleaseWatch collector coroutines, but the LocalOnlyHotspotReservation and the process-wide bindProcessToNetwork are never released.
- **Impact:** After kit.stop() (or a restart cycle) the soft-AP reservation stays open: Wi-Fi radio stays in AP mode, the random SSID keeps broadcasting, battery drains, and if a join was active the process-wide bindProcessToNetwork stays pinned to an internet-less network so all subsequent sockets route through a stale network. Repeated start/stop accumulates orphaned reservations. Also directly contradicts the KDoc on close() (lines 230-235) and ProvisioningContext.parentJob (NetworkProvisioningFactory.kt:60-67) which both claim stop() releases reservations.
- **Fix:** Either (a) add `scopeJob.invokeOnCompletion { runCatching { handle?.close() }; runCatching { joinHandle?.close() } }` at construction (make the fields @Volatile so the completion handler reads the latest write), or (b) make P2pKitImpl.stop() explicitly invoke `(networkProvisioning as? AutoCloseable/Closeable)?.close()`. Add a unit test with a fake WifiManagerWrapper asserting the reservation's close() is invoked when the parent job is cancelled.

## 🟠 High findings

#### 🟠 `ios-replay0-flow-late-subscribe-missed-messages` — iOS attaches incoming collector via 1s poll / post-connect, and NEVER subscribes to incomingFiles
- **File:** `iosApp/ContentView.swift:463-479, 600-602, 625, 665, 723`
- **Category:** correctness · **Fix validation:** ✅ no hardware needed *(severity/scope adjusted by verifier)*
- **Problem:** session.incoming and incomingSessions are SharedFlow replay=0 (P2pSession.kt:42, P2pSessionImpl.kt:120-122; incomingSessions in SessionManager.kt:109-111) — pre-subscription emissions are not buffered. On iOS the incoming collector attaches via: (a) the incomingSessions detached task (463-472) for inbound, (b) attachMessageCollector AFTER connect() resolves (665, 723), and (c) the 1s pollTask (474-479 → refreshPeersAndSessions → 600-602 spawning attachMessageCollector for newly-seen sessions). Path (c) gives up to a 1s window where peer-sent messages are dropped before subscription. CRITICALLY: ContentView.swift contains no `incomingFiles` collector at all (grep confirms zero references), so iOS can never receive a file offer — every inbound offer auto-rejects after the 30s offerTimeout. The desktop sample has wireIncomingFiles; iOS has no equivalent.
- **Impact:** On iOS the first message(s) of a freshly-discovered session can be lost (up to 1s), and no inbound file transfer is ever possible. A correctness gap consumers will copy from the published reference sample.
- **Fix:** Attach the message collector event-driven the moment a session first appears rather than via the 1s poll (subscribe to kit.sessions via a FlowCollector adapter and call attachMessageCollector synchronously on first observation). Add an incomingFiles collector mirroring the desktop wireIncomingFiles so iOS can accept offers. Longer term, a small replay/buffer on incoming in the SDK would make late subscription safe.

#### 🟠 `kit-single-use-after-stop` — stop() permanently cancels the internal scope; a later start()/startAdvertising() silently returns success but the kit is dead
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/P2pKit.kt:173-174`
- **Category:** correctness · **Fix validation:** ✅ no hardware needed
- **Problem:** P2pKitImpl.stop() (352-363) calls internalJob.cancel() (361), cancelling the SupervisorJob backing `scope` (built at 75-76) that powers SessionManager, PeerRegistry, the path-observer subscription, and per-session scopes. Nothing recreates internalJob/scope. startResult stays Result.success(Unit) from the prior start, so a subsequent start() short-circuits in ensureStarted() at 242-244 and returns immediately without rebinding — yet every coroutine the kit needs is cancelled. No public KDoc marks the instance single-use; P2pKit.start KDoc (119-132) says 'Idempotent ... After a failed start, the next call retries', and States.kt implies stop()->Idle (reusable).
- **Impact:** A host doing stop() on background then start()/startAdvertising() on foreground gets a zombie kit: start() returns success but discovery/sessions never function and no error is thrown. This is the documented background/foreground lifecycle pattern, silently dead.
- **Fix:** Pick one: (a) document P2pKit as single-use and have post-stop lifecycle calls throw IllegalStateException; or (b) make stop() recreate internalJob/scope, reset startResult=null, reset _state to Idle so the instance is genuinely reusable. Align KDoc on start/stop and States.kt with the chosen contract.

#### 🟠 `state-lifecycle-contract-violated` — P2pState documented lifecycle does not match what P2pKitImpl emits (start/connect never reach Running; Failed never emitted; stop sets Stopped not Idle)
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/States.kt:3-16`
- **Category:** api-design · **Fix validation:** ✅ no hardware needed
- **Problem:** States.kt:6-7 KDoc declares 'Idle -> Starting -> Running -> Stopping -> Stopped' and 'Failed is terminal until stop() which returns to Idle'. Verified against P2pKitImpl: (1) start()/ensureStarted() (225-280) never write _state — only startAdvertising() sets Starting (285) then Running (296). A host calling only start()+connect() leaves state==Idle while fully running. (2) startDiscovery() (305-311) and connect() (319-329) never set Running. (3) P2pState.Failed is never emitted anywhere in P2pKitImpl — ensureStarted() throws TransportStartFailed on bind failure (259) and leaves _state at Idle; the documented Failed-terminal branch and Errors.kt:41-45's claim that TransportStartFailed 'surfaces through the kit lifecycle' are dead. (4) stop() sets Stopped (362), never Idle, contradicting 'stop() returns to Idle'.
- **Impact:** Host apps driving UI off state (the documented 'offline banner' / lifecycle use) read wrong values: a running kit reads Idle, a failed start reads Idle (not Failed), a stopped kit reads Stopped (not Idle). Any host `when(state){ Running->...; Failed->showError }` is broken against the published contract.
- **Fix:** Make ensureStarted() drive state: Starting at entry, Running on success, Failed(P2pError.TransportStartFailed) before throwing on bind failure. Reconcile stop() vs KDoc (either reset to Idle or document Stopped as terminal). Document that Running is reached by start(), not only startAdvertising().

#### 🟠 `blocking-sink-write-on-route-loop` — onFileData performs synchronous sink.write on the single routeEvents coroutine, stalling PING/PONG/CLOSE
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/internal/FileTransferDispatcher.kt:351-377`
- **Category:** concurrency · **Fix validation:** ✅ no hardware needed
- **Problem:** routeEvents (P2pSessionImpl.kt:437-515) is one coroutine per epoch processing ALL inbound frames serially; it awaits fileTransferDispatcher.onFileData(event.frame) inline at line 497. onFileData calls recv.acceptDataChunk(frame) (FileTransferDispatcher.kt:365) which calls the non-suspending blocking sink.write(frame.payload) (StreamingFileReceiver.kt:62). For the convenience accept paths the sink is a buffered file/OutputStream sink, so a slow disk blocks the very coroutine responsible for replying PONG and handling CLOSE. There is no IO dispatcher hop and no per-transfer writer coroutine.
- **Impact:** Receiving a large file to slow storage starves keep-alive/control-frame processing on that epoch, which can trip the peer's keep-alive timeout (keepAliveLoop relies on inbound PONG and outbound PONG replies) and drop the session mid-transfer — exactly the workload the feature exists for.
- **Fix:** Decouple inbound file writes from the route loop: feed each FILE_DATA payload to a per-transfer bounded channel drained by a dedicated writer coroutine (with backpressure), or at minimum move the blocking sink.write to a dedicated IO dispatcher. Keep PING/PONG/CLOSE responsive on the route loop.

#### 🟠 `ondata-failure-uncaught-nonp2p` — onFileData only catches P2pError; a sink IOException escapes and tears down the whole session
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/internal/FileTransferDispatcher.kt:364-377`
- **Category:** error-handling · **Fix validation:** ✅ no hardware needed
- **Problem:** onFileData wraps acceptDataChunk in `try { ... } catch (e: P2pError)` (lines 364-367). acceptDataChunk calls sink.write(...) (StreamingFileReceiver.kt:62) which throws kotlinx-io IOException on disk-full / closed-fd / IO error — NOT a P2pError. That exception is not caught here; it propagates out of onFileData into the routeEvents collect loop, hits the generic catch (P2pSessionImpl.kt:511) and calls onConnectionLost, killing the entire session (and every other transfer/message) because one receiver's disk filled up.
- **Impact:** A receiver-side disk error on a single file transfer brings down the whole session rather than failing just that transfer. Disproportionate blast radius; disk-full is common in production. Raised to high (matching the session-teardown blast radius and how routine the trigger is).
- **Fix:** Catch Throwable (rethrowing CancellationException) in onFileData, map non-P2pError to Failed(IoFailure/ConnectionFailed), remove the entry, abort the receiver, and best-effort send FILE_CANCEL — never let a per-transfer I/O error escape into routeEvents.

#### 🟠 `reconnect-rewrites-midstream` — In-flight transfers survive reconnect and write mid-stream chunks onto the new connection
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/internal/FileTransferDispatcher.kt:332,449-481`
- **Category:** correctness · **Fix validation:** ✅ no hardware needed
- **Problem:** The dispatcher is built with the session-level scope (P2pSessionImpl.kt:163 passes `scope = scope`, the CoroutineScope bound to sessionJob at line 115, not the epoch scope). The outgoing streamer is launched via `scope.launch { streamOutgoingPayload(handle) }` (FileTransferDispatcher.kt:332), so it is a child of sessionJob, not epochJob. On reconnect, rearmWith (P2pSessionImpl.kt:289-309) cancels ONLY epochJob (line 295) and then swaps `connection = newConnection` (line 297); it does NOT call fileTransferDispatcher.closeAll. getConnection is wired as `{ connection }` (line 159) reading the swapped field. Consequently a streamOutgoingPayload coroutine that was mid-stream on epoch N keeps running and its next `sendMutex.withLock { protocol.sendFileDataFrame(getConnection(), frame) }` (lines 460-461) writes the next FILE_DATA chunk onto the brand-new epoch N+1 connection. The receiver on the new connection has nextExpectedIndex=0 and rejects the out-of-order chunk (StreamingFileReceiver.kt:49). Note transitionToTerminal DOES call closeAll (P2pSessionImpl.kt:382) — so only the reconnect (rearm) path leaks this, which is exactly the ReconnectPolicy.Enabled scenario.
- **Impact:** Any outgoing file transfer in progress when the LAN link blips and reconnects is corrupted: stale chunks land on the new connection producing confusing out-of-order ProtocolErrors on the receiver, rather than a clean Failed/restart. Data-integrity bug on the core feature under the explicitly-supported reconnect scenario.
- **Fix:** In rearmWith, before startEpoch, call fileTransferDispatcher.closeAll("reconnect") to fail all in-flight transfers (matching the closeAll-on-terminal contract that transitionToTerminal already follows). Alternatively bind each transfer's writes to a captured epoch connection / epoch scope so they are cancelled with epochJob. Option (a) is simplest and consistent with the documented terminal semantics.

#### 🟠 `blocking-io-on-construct-thread` — PeerId storage performs blocking file I/O on the P2pKit.create{} caller thread
- **File:** `p2p-core/src/commonMain/kotlin/dev/p2pkit/core/internal/P2pKitImpl.kt:392-398`
- **Category:** performance · **Fix validation:** ✅ no hardware needed
- **Problem:** newP2pKit() calls peerIdStorage.loadOrGenerate() synchronously at construction (P2pKitImpl.kt:398), and the whole entry path is non-suspend: P2pKit.create{} (P2pKit.kt:184) -> P2pKitBuilder.build() (Builders.kt:114) -> newP2pKit(). On Android/JVM, FilePeerIdStorage.loadOrGenerate() does storageFile.exists(), readText(), mkdirs(), writeText() and a renameTo on the calling thread. P2pKitAndroid kdoc steers init to Application.onCreate() (main thread). This is a StrictMode disk-read/write violation and a cold-start jank/ANR risk on slow or encrypted storage.

#### 🟡 `no-untrusted-length-cap-on-read` — write() has no socket write timeout; a peer that stops draining its TCP window wedges the writer coroutine and the keep-alive PING forever
- **File:** `p2p-transport-lan/src/jvmMain/kotlin/dev/p2pkit/transport/lan/JvmRawConnection.kt:34-42`
- **Category:** robustness · **Fix validation:** ✅ no hardware needed
- **Problem:** Verified against the actual code. write() (lines 34-42) does `out.write(bytes); out.flush()` inside `writeLock.withLock { withContext(Dispatchers.IO) { ... } }` with no timeout and no socket-level write deadline. SO_TIMEOUT is never set (no setSoTimeout call anywhere in the file). I confirmed in P2pSessionImpl that keepAliveLoop (line 522) sends PINGs via `sendMutex.withLock { protocol.sendPing(epochConnection) }`, i.e. through the same serialized write path. If a peer accepts the connection and never reads, the kernel TCP send buffer fills, the blocking `out.write` parks indefinitely holding the write mutex, and the keep-alive PING write also blocks rather than timing out — so observeRawState never sees a terminal raw state and the session is not driven to Failed via the write path. The read-side analysis in the original title is correct and benign; the real gap is the missing write deadline.
- **Impact:** A single misbehaving or malicious LAN peer can block a session's writer coroutine and starve the keep-alive PING by accepting a connection and never draining it, holding the TCP send window full. The session's write path can wedge with no timeout to break it.
- **Fix:** Add a bounded write deadline: wrap the blocking write in `withTimeout(WRITE_TIMEOUT_MS)` inside write(); on timeout close the socket and set `_state.value = ConnectionState.Failed` so observeRawState triggers terminal/reconnect. Document the constant alongside TCP_CONNECT_TIMEOUT_MS. Mirror in AndroidRawConnection. Validatable with a unit test using a non-draining ServerSocket; no hardware needed.

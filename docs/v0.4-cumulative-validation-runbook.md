# v0.4 Cumulative Validation Runbook

Hardware-execution runbook for the seven tests gating v0.4 runtime-foundation sign-off:
**R1, R2, R3, R4** (required) + **E1, E2, E4** (high-value edge cases). Each test is
deterministic, isolatable, and attributable to specific subsystems.

## Pre-flight (do once, before any test)

### Build the artifacts correctly

**Critical:** the iOS Xcode project consumes the **XCFramework**, not the single-arch
framework. The correct build commands are:

```bash
# Android — produces APK consumed directly by adb install:
./gradlew :p2p-sample-android:assembleDebug

# iOS — produces the XCFramework Xcode links against:
./gradlew :p2p-transport-lan:assembleP2pKitSharedReleaseXCFramework
```

**Do NOT use `:p2p-transport-lan:linkIosArm64`.** That produces a single-arch
framework at `build/bin/iosArm64/releaseFramework/` which Xcode does NOT consume.
The iOS project's `FRAMEWORK_SEARCH_PATHS` points to
`build/XCFrameworks/release/P2pKitShared.xcframework`, populated only by
`assembleP2pKitSharedReleaseXCFramework`. Using the wrong task will silently
deploy pre-change code to the device while the Gradle build claims success.

Verify the XCFramework is fresh against the latest commit:

```bash
ls -la p2p-transport-lan/build/XCFrameworks/release/P2pKitShared.xcframework/ios-arm64/P2pKitShared.framework/P2pKitShared
# Compare timestamp to: git log -1 --format=%ai
```
The framework timestamp MUST be newer than the latest commit you intend to test.

### Deploy

- **Android:** `adb install -r p2p-sample-android/build/outputs/apk/debug/p2p-sample-android-debug.apk`
- **iPhone:** in Xcode — quit Xcode, `rm -rf ~/Library/Developer/Xcode/DerivedData/p2pkit-sample-*`,
  re-open Xcode, Product → Clean Build Folder (⇧⌘K), connect device, Product → Run (⌘R).

### Verify the deployment landed BEFORE running any test

When the iPhone app launches, the FIRST kit-startup log lines MUST include:

```
p2pkit: [data] buildListener: nw_listener_create            ← present only post-V0.4-IOS-LISTENER-REBIND
p2pkit: [data] buildListener: SUCCESS port=<N>
p2pkit: [data] start: SUCCESS port=<N>
p2pkit: [data] startPathMonitor: monitor started            ← present only post-V0.4-IOS-LISTENER-REBIND
```

If `startPathMonitor: monitor started` is missing, the iPhone is running stale
framework code. STOP and rebuild the XCFramework + Xcode clean-and-deploy.

The Android equivalent: on `kit started`, the log line must read
`reconnect=Enabled(maxAttempts=5, retryDelayMillis=1000)` (or whichever
non-Disabled policy the sample is configured for). `reconnect=Disabled`
bypasses V0.4-RECONNECT entirely and invalidates any test that depends on it.

### Devices
- **Android** test device flashed with the cumulative APK.
- **iPhone** test device with the Xcode-built sample app linked against the fresh
  XCFramework (verified via the startup-log check above).
- Both devices on the **same home Wi-Fi network** initially, both apps **force-quit**
  before each test begins (cold start eliminates carry-over state).

### Log capture tooling

**Android — open in a terminal before each test, leave running:**
```bash
adb logcat -c            # clear backlog
adb logcat -v time \
    p2pkit:* P2pKitNsd:* AndroidRuntime:E *:S \
    > ~/v0.4-validation/<test-id>-android.log &
```
The `*:S` silences everything else. `AndroidRuntime:E` catches any uncaught exceptions
(including `kotlin.IllegalStateException` from SessionStore invariants).

**iPhone — Xcode console attached, copy on demand:**
- Xcode → Window → Devices and Simulators → select iPhone → View Device Logs
  (or simply use the running Xcode console pane if the app is launched from Xcode).
- Save each test's output to `~/v0.4-validation/<test-id>-iphone.log` by copying the
  full session log when the test ends.
- The kit's `p2pkit:` prefix on every line makes filtering trivial.

### Global STOP conditions

If ANY of the following appears in EITHER log during ANY test, **stop immediately**,
preserve all logs, and report back before continuing:

- `kotlin.IllegalStateException: SessionStore[...]:` — S1 invariant violation.
- `ZOMBIE` warning (zombie-session watchdog, P2pSessionImpl).
- `STUCK` warning (stuck-Reconnecting watchdog).
- Process crash / `AndroidRuntime: FATAL EXCEPTION` / iOS app termination.
- Duplicate session for same peer in `kit.sessions` (visible in Android Logcat as
  two `session added` lines for the same peer id without an intervening `removed`).

These are unambiguous regressions of S1 / S3 / V0.4-RECONNECT correctness.

### General principles

1. **Cold start each test.** Force-quit both apps between tests. The cooldown periods
   listed in each test exist to let iOS's mDNSResponder daemon and Android's NSD
   service reach quiescent state.
2. **One initiator per test.** Tests specify which side calls `connect()` — this
   matters because the reconnect handler is wired only on the outgoing side. E4
   specifically swaps the initiator to exercise the alternate code path.
3. **Don't touch the apps mid-test.** Once the trigger is applied, watch passively
   for the recovery window. Interaction can mask whether automatic recovery actually
   worked.
4. **One test at a time.** If a test fails, the cause is attributable to one
   subsystem. If you run two tests back-to-back without cooldown, attribution becomes
   ambiguous.
5. **Capture aggregate counts.** At the end of all seven tests, grep each log for
   `STOP-condition` strings and report counts.

## R1 — Test 3: Hotspot switch (cumulative)

**Subsystems validated:** V0.4-NSD (Android NSD rebind), V0.4-AP (default-network callback
for hotspot-host transitions), V0.4-IPV6 (selector rejects unscoped `fe80::`),
V0.4-RECONNECT (per-attempt InternalPeer re-resolution), V0.4-IOS-LISTENER-REBIND
(iOS listener+browser rebind on path-satisfied-after-change), Bonjour identity stability.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.
- Android hotspot OFF.
- Android Wi-Fi ON, joined to home network.

**Initiator:** Android (exercises V0.4-RECONNECT on the Android side).

**Setup:** Clean app launch on both sides.

**Steps:**
1. Start Logcat capture: `adb logcat -c && adb logcat -v time p2pkit:* P2pKitNsd:* AndroidRuntime:E *:S > ~/v0.4-validation/r1-android.log &`
2. Launch Android app. Wait 3s.
3. Launch iPhone app. Wait 5s.
4. Confirm both apps show each other in the peer list.
5. On Android: tap "Connect" on the iPhone peer card. Wait for "Connected" state.
6. On Android: type `r1-msg1`, tap Send. Verify iPhone receives.
7. On iPhone: type `r1-reply1`, tap Send. Verify Android receives.
8. **Trigger:** On Android, open quick-settings → turn off Wi-Fi → turn on Hotspot/Tethering.
   (Use the password you've set on the Android hotspot; if first time, set one now.)
9. Wait ~5 seconds for the hotspot to come up.
10. **Trigger:** On iPhone, open Settings → Wi-Fi → join the Android hotspot SSID.
11. **Do not interact with either app for 60 seconds.**
12. After 60s: on Android, verify the iPhone shows as "Connected" in the peer list.
13. On Android: type `r1-msg2`, tap Send. Verify iPhone receives.
14. Save iPhone Xcode console output to `~/v0.4-validation/r1-iphone.log`.

**Expected timing (relative to step 8, hotspot trigger = T+0):**

| Event | Window |
|---|---|
| Android Wi-Fi off, hotspot up | T+0 to T+5s |
| iPhone joins hotspot | T+5s to T+10s |
| Android: `NetworkCallback.onLost: 203` | T+~5s |
| Android: `DefaultNetworkCallback.onLost: 203 (default cleared)` | T+~5s |
| Android: `rebindNow: starting; reason=default network lost...` | T+~6s (after 800ms debounce) |
| Android: `rebindNow: complete` | T+~7s |
| iPhone: `path-monitor: ... becameSatisfied=true isFirst=false` | T+~6-10s |
| iPhone: `data: rebindNow: starting` | T+~7-11s (after 800ms debounce) |
| iPhone: `data: rebindNow: complete (port rotated: X -> Y)` | T+~8-12s |
| Android: `auto-mesh: initiating connect to iPhone` (with fresh hint) | T+~10-15s |
| Android: `session iPhone → Connected` | T+~12-18s |
| Message round-trip works | T+~15-25s |

**Hard ceiling:** 60 seconds. If session isn't Connected at T+60s, this is a **FAIL**.

**Success signatures — Android Logcat (all must appear):**

**Success signatures — iPhone Xcode console (all must appear):**

**Failure signatures (any of these is a FAIL):**

**Cooldown before R2:**
1. On iPhone: rejoin home Wi-Fi (Settings → Wi-Fi → tap home network).
2. On Android: turn off Hotspot. Turn on Wi-Fi. Wait until joined to home network.
3. Force-quit both apps.
4. Stop Logcat capture.
5. Wait 30 seconds (iOS mDNSResponder quiescence).

## R3 — Test 2: Reconnect storm (re-run on v0.4)

**Subsystems validated:** Debounce coalescing under sustained churn, V0.4-RECONNECT
re-resolution across multiple attempts, iOS listener port rotation under repeated
cycles (file-descriptor leak check), Android NSD subscription longevity, S1
invariants across 6 sequential transitions.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.

**Initiator:** Android.

**Setup:** Clean app launch.

**Steps:**

Initial setup:
1. Start Logcat to `~/v0.4-validation/r3-android.log`.
2. Launch both apps, establish session, confirm message exchange (`r3-baseline`).

Then 6 toggle cycles. For each cycle N (1..6), do:

**Cycle 1 — Android Wi-Fi:**
- Wi-Fi OFF on Android. Wait 5s. Wi-Fi ON. Wait up to 30s.
- Verify Connected on both sides.
- Send `r3-c1-msg` from Android.

**Cycle 2 — Android Wi-Fi (again):**
- Same as cycle 1 but second iteration.
- Send `r3-c2-msg`.

**Cycle 3 — iPhone Wi-Fi:**
- Wi-Fi OFF on iPhone. Wait 5s. Wi-Fi ON. Wait up to 30s.
- Verify Connected.
- Send `r3-c3-msg`.

**Cycle 4 — iPhone Wi-Fi (again):**
- Same pattern.
- Send `r3-c4-msg`.

**Cycle 5 — Both simultaneously:**
- Wi-Fi OFF on Android AND iPhone simultaneously. Wait 5s.
- Wi-Fi ON on Android AND iPhone simultaneously. Wait up to 60s.
- Verify Connected.
- Send `r3-c5-msg`.

**Cycle 6 — Both, faster:**
- Wi-Fi OFF on both. Wait 3s only. Wi-Fi ON on both. Wait up to 60s.
- Verify Connected.
- Send `r3-c6-msg`.

Save iPhone log to `~/v0.4-validation/r3-iphone.log`.

**Total expected time:** ~7 minutes (1 min between cycles for stabilization).

**Aggregate success criteria:**

| Criterion | Expected |
|---|---|
| Successful recoveries | 6 / 6 cycles |
| Final session state | Connected |
| Final message exchange | Works both directions |
| iPhone NWListener `rebindNow: complete` count | ≥4 (at least 4 of 6 cycles trigger iOS rebind — both-side cycles plus iPhone-only cycles) |
| Android `rebindNow: complete` count | ≥4 (Android-only cycles plus both-side cycles) |
| `REBUILD FAILED` count | 0 |
| `REBUILD OK but ... hook FAILED` count | 0 |
| `SessionStore[...]` check() failures | 0 |
| ZOMBIE / STUCK warnings | 0 |
| `Reconnect target changed` lines | ≥4 (V0.4-RECONNECT firing on rotation) |
| Unique iPhone listener ports observed | Should rotate, 4+ distinct values |
| Process memory (Android) at end vs start | < 50 MB delta (loose ceiling) |

**Failure signatures (any of these is a R3 FAIL):**
- Any cycle N+1 fails where cycle N succeeded (state-accumulation regression).
- iPhone permanently loses NWListener mid-test.
- Any STOP-condition log line.
- Final message exchange doesn't work.

**Cooldown before R4:**
1. Force-quit both apps.
2. Both devices on home Wi-Fi.
3. Wait 30 seconds (longer than other cooldowns — multiple rotations leave residual
   mDNS state).

## R4 — Test 4: Background/foreground churn

**Subsystems validated:** iOS path monitor behavior during app background suspension,
`hasEverObservedSatisfied` first-signal-skip on foreground return (no false rebind
storm), `BackgroundPolicy.CloseActiveSessions` semantics, session re-establishment
after foreground.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.

**Initiator:** Android.

**Setup:** Clean app launch.

**Steps:**
1. Start Logcat to `~/v0.4-validation/r4-android.log`.
2. Launch both apps, establish session, send `r4-pre-bg` message, confirm.
3. **Trigger 1:** On iPhone, swipe up from bottom (home gesture) to background the app.
4. Wait 30 seconds. (iOS will suspend the app; `BackgroundPolicy.CloseActiveSessions`
   will close existing sessions on the next path event or on resume.)
5. **Trigger 2:** On iPhone, tap the app icon to foreground it.
6. Wait 15 seconds. Observe both Xcode console and Android Logcat.
7. From Android, send `r4-post-bg` message.
   - Expected: a NEW session forms automatically via auto-mesh. Send may need a few
     seconds to land on a Connected session.
8. **Trigger 3:** Repeat steps 3-5 once more (second bg→fg cycle).
9. After foreground, wait 15s. Send `r4-post-bg2` from Android, confirm.
10. Save iPhone log to `~/v0.4-validation/r4-iphone.log`.

**Expected behavior:**
- On background: iOS may suspend the kit's coroutine scopes. Existing sessions
  transition through Closed via `BackgroundPolicy.CloseActiveSessions`. The iOS path
  monitor may or may not fire callbacks during suspension — that's an Apple-level
  decision.
- On foreground: app process resumes. Path monitor may fire `satisfied`. The
  `hasEverObservedSatisfied` flag was set BEFORE backgrounding, so a satisfied
  signal post-foreground is NOT a first-signal — but it's also NOT a true
  "became-satisfied-after-unsatisfied" because the suspended app didn't observe
  the unsatisfied state. So a foreground-fired satisfied with prev=satisfied
  should be a no-op (`becameSatisfied=false`).
- No rebind storm on foreground.

**Success signatures — iPhone:**
```
[On background trigger:]
p2pkit: [session] removed id=in-...   (BackgroundPolicy closed session)
[Optional during background — Apple may pause delivery:]
p2pkit: [data] path-monitor: status=... (any value, informational)

[On foreground:]
[Either NO rebind line:]
p2pkit: [data] path-monitor: status=1 isSatisfied=true becameSatisfied=false isFirst=false
[OR a single legitimate rebind:]
p2pkit: [data] rebindNow: starting (path satisfied after change ...)
p2pkit: [data] rebindNow: complete

[After foreground, session re-establishment:]
p2pkit: [browse] emitPeer: ACCEPTED Found Android-...
p2pkit: [data] listener: accepted inbound nw_connection
p2pkit: [session] new id=in-... state=Connected
```

**Failure signatures:**
```
iPhone: multiple rebindNow: starting lines on foreground return without intervening
        path changes (rebind storm — first-signal-skip broken)
iPhone: data: rebindNow: REBUILD FAILED on foreground (listener can't rebuild)
iPhone: data: listener state -> failed after foreground (permanent listener death)
Both messages r4-post-bg and r4-post-bg2 fail to deliver within 30s of foreground
Any STOP-condition
```

**Cooldown before E1:**
1. Force-quit both apps.
2. Both devices on home Wi-Fi.
3. Wait 15 seconds.

## E1 — Rapid hotspot toggles

**Subsystems validated:** Debounce coalescing under sub-window rapid changes,
`pendingRebindJob` cancel-supersede correctness on Android (V0.4-NSD + V0.4-AP)
and iPhone (V0.4-IOS-LISTENER-REBIND). Validates that 5 toggles inside ~30s
collapse to 1-2 actual rebind cycles, not 5.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.
- Android hotspot OFF.

**Initiator:** Android.

**Setup:** Clean app launch.

**Steps:**
1. Start Logcat to `~/v0.4-validation/e1-android.log`.
2. Launch both apps, establish session, send `e1-pre` message, confirm.
3. **Toggle sequence (do not wait for any settling between sub-steps):**
   - On Android: toggle Hotspot ON. (~2s)
   - On Android: toggle Hotspot OFF.
   - Wait 3s.
   - On Android: toggle Hotspot ON.
   - On Android: toggle Hotspot OFF.
   - Wait 3s.
   - On Android: toggle Hotspot ON.
   - On Android: toggle Hotspot OFF.
   - Wait 3s.
   - On Android: toggle Hotspot ON.
   - On Android: toggle Hotspot OFF.
   - Wait 3s.
   - On Android: toggle Hotspot ON.
   - On Android: toggle Hotspot OFF.
4. **Settle:** Wait 60 seconds without touching anything.
5. Verify Android is back on home Wi-Fi.
6. On Android: tap Connect on iPhone if not already connected. Wait for Connected.
7. Send `e1-post` message, confirm both directions.
8. Save iPhone log to `~/v0.4-validation/e1-iphone.log`.

**Note:** The iPhone may or may not have joined the hotspot during the toggle storm
— that's fine, the test is about debounce on the Android side primarily.

**Aggregate success criteria:**

| Criterion | Expected |
|---|---|
| `scheduleRebind` lines (Android) | 5-10 (one per toggle, possibly more from default callback) |
| `rebindNow: starting` lines (Android) | **1-3** (≪ scheduleRebind count = debounce working) |
| `rebindNow: complete` lines (Android) | matches `rebindNow: starting` count |
| `scheduleRebind` lines (iPhone) | 0-5 (depends on whether iPhone saw path changes) |
| `rebindNow: starting` lines (iPhone) | **0-2** (≪ scheduleRebind count) |
| Final session | Connected |
| Final message exchange | Works |
| `REBUILD FAILED` | 0 |

## E3 — Repeated rotations (slow cadence)

**Subsystems validated:** Resource-leak detection across the full rebind lifecycle.
Distinct from E1 (sub-debounce-window fast toggles, ~3s apart) — E3 lets each rebind
cycle complete fully before the next, exercising 8 sequential complete rebind cycles
to catch slow leaks. Specifically: Android NSD subscription accumulation, per-rebind
listener-port rotation, peer-registry cleanup correctness, no SessionStore state
drift across 8+ session creation/teardown cycles.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.
- Both devices on >40% battery (8 rotations over ~8 minutes drains noticeable battery).

**Initiator:** Android.

**Setup:** Clean app launch.

**Steps:**

Initial:
1. Start Logcat to `~/v0.4-validation/e3-android.log`.
2. Launch both apps, establish session, send `e3-baseline` message both ways.
3. Take baseline memory snapshot:
   ```bash
   adb shell dumpsys meminfo dev.p2pkit.sample.android | grep -E "TOTAL PSS|Native Heap" > ~/v0.4-validation/e3-mem-baseline.txt
   ```

Cycle loop — repeat for cycles 1..8:

For each cycle N:
1. On Android: turn Wi-Fi OFF.
2. Wait 5 seconds.
3. On Android: turn Wi-Fi ON.
4. Wait 30 seconds for full recovery — do NOT touch anything.
5. Verify session shows Connected.
6. Send `e3-c<N>-msg` from Android.
7. Confirm iPhone receives within 5s.

After cycle 8:
1. Take final memory snapshot:
   ```bash
   adb shell dumpsys meminfo dev.p2pkit.sample.android | grep -E "TOTAL PSS|Native Heap" > ~/v0.4-validation/e3-mem-final.txt
   ```
2. Save iPhone log to `~/v0.4-validation/e3-iphone.log`.

**Expected timing:** Each cycle ~35-40s. Total ~6-7 minutes plus initial setup.

**Hard ceiling:** 12 minutes total. Any individual cycle that fails to recover
within 60s of Wi-Fi back on is a FAIL.

**Aggregate success criteria:**

| Criterion | Expected |
|---|---|
| Cycles succeeded | **8 / 8** |
| Successful message exchanges post-cycle | **8 / 8** |
| `P2pKitNsd: rebindNow: complete` count | **8** (one per Wi-Fi return) |
| iPhone `data: rebindNow: complete` count | **0** (iPhone Wi-Fi never toggled in E3 — iPhone path-monitor sees Android peer disappear and reappear, but iPhone's own path stays satisfied) |
| `REBUILD FAILED` | **0** |
| `SessionStore[...]:` check() failures | **0** |
| ZOMBIE / STUCK / FATAL | **0** |
| Android `TOTAL PSS` delta (baseline → final) | **< 30 MB** (loose ceiling — real leaks are usually 10x larger) |
| `Reconnect target changed` lines | ≥ 6 (V0.4-RECONNECT firing — iPhone address may or may not actually change but the registry-vs-original comparison fires) |
| Peer-registry stale entries at end | 0 (just one iPhone peer, no duplicates) |

**Failure signatures:**

- Cycle N+1 fails where cycle N succeeded → state-accumulation regression. Capture
  the cycle number and the exact failure log.
- Android `TOTAL PSS` delta > 30 MB → likely leak. Capture both meminfo dumps.
- `P2pKitNsd: rebindNow: complete` count < 8 → some rebind cycles were skipped
  unexpectedly. Capture which scheduling lines fired without matching completion.
- `data: rebindNow: complete` count > 0 on iPhone → unexpected iPhone rebind
  during E3 (iPhone's path was stable; this would indicate iPhone's path monitor
  is firing on transient inter-device mDNS state, which is a regression).
- Any STOP-condition.

**Cooldown after E3:**
1. Force-quit both apps.
2. Both devices on home Wi-Fi.
3. Wait 60 seconds (E3 leaves the most residual state of any test — extended cooldown
   ensures clean baseline for any subsequent run).

## E4 — Asymmetric initiation (iPhone-initiated session + rotation)

**Subsystems validated:** Reverse-direction session lifecycle. When iPhone initiates,
the OUTGOING session on iPhone has the reconnect handler (V0.4-RECONNECT applies),
and the Android side is INCOMING (no reconnect handler — goes directly to Failed).
After rotation, recovery happens via two competing paths: iPhone's reconnect handler
AND Android's auto-mesh. Tests simultaneous-open arbitration under rotation.

**Pre-conditions:**
- Both apps force-quit.
- Both devices on home Wi-Fi.

**Initiator:** **iPhone (this is the key difference from R1-R3).**

**Setup:** Clean app launch.

**Steps:**
1. Start Logcat to `~/v0.4-validation/e4-android.log`.
2. Launch both apps, wait 5s for discovery.
3. **On iPhone, NOT Android:** tap Connect on the Android peer card. (iPhone initiates.)
4. Wait for Connected on both sides.
5. Send `e4-msg1` from iPhone, confirm Android receives.
6. Send `e4-reply1` from Android, confirm iPhone receives.
7. **Trigger:** On iPhone, toggle Wi-Fi OFF. Wait 5s. Wi-Fi ON.
8. Wait up to 60 seconds.
9. Verify session Connected (regardless of which side "won" any simultaneous-open).
10. Send `e4-msg2` from iPhone, confirm.
11. Send `e4-reply2` from Android, confirm.
12. Save iPhone log to `~/v0.4-validation/e4-iphone.log`.

**Expected behavior — two competing recovery paths converge:**

After iPhone Wi-Fi rejoin:
- **Path A (iPhone-side reconnect handler):** iPhone outgoing session was in
  Reconnecting; after path-satisfied, the handler re-dials Android. V0.4-RECONNECT
  re-resolves the InternalPeer for Android from PeerRegistry (fresh after iPhone
  rejoined and saw Android's mDNS).
- **Path B (Android-side auto-mesh):** Android's incoming session went directly to
  Failed (no reconnect handler). After iPhone rejoined, Android's NSD sees iPhone
  re-advertise. PeerRegistry fires Found. Auto-mesh initiates a connect to iPhone.

Both paths may execute concurrently → **simultaneous-open**. The S1 arbitration
rule kicks in: smaller-peer-id keeps OUTGOING, larger keeps INCOMING. The loser
session is closed, leaving exactly one session for the peer.

**Success criteria:**
- Exactly one session per peer at the end.
- Message exchange works in both directions.
- Logs show simultaneous-open arbitration may have fired (look for
  `Simultaneous-open for peer ... promoting/rejecting`); this is informational,
  not a failure.

**Success signatures — Android:**
```
[Pre-rotation:]
p2pkit: room: session added iPhone   (incoming session: id starts with "in-...")
p2pkit: session iPhone → Connected
p2pkit: registerSession in peer=f9d1f0ba decision=Accepted

[On rotation:]
p2pkit: session iPhone → Closed   (incoming has no reconnect handler → terminal)
p2pkit: room: session removed iPhone

[After rotation:]
[Either:]
p2pkit: auto-mesh: initiating connect to iPhone
p2pkit: registerSession out peer=f9d1f0ba decision=Accepted   (no simultaneous open)
p2pkit: session iPhone → Connected
[OR with simultaneous open:]
p2pkit: registerSession <direction> peer=f9d1f0ba decision=Replaced  (or Rejected)
p2pkit: Simultaneous-open for peer f9d1f0ba: <promoting / rejecting> new <direction> session ...
p2pkit: session iPhone → Connected   (final winner)
```

**Success signatures — iPhone:**
```
[Pre-rotation:]
p2pkit: [session] new id=out-02e2b397-... peer=02e2b397 state=Connected

[On rotation — path monitor + reconnect handler:]
p2pkit: [data] path-monitor: ... becameSatisfied=true isFirst=false
p2pkit: [data] rebindNow: complete (port rotated ...)
[Reconnect handler re-dial via V0.4-RECONNECT:]
[Either reconnect succeeds with fresh hint, or simultaneous-open arbitration leaves
 iPhone with an incoming session in place of its outgoing — both outcomes are
 acceptable end-states.]
```

**Failure signatures:**
- Both sides stuck with no live session at T+60s after rotation.
- Two simultaneously-live sessions for the same peer (visible as duplicate
  `session added` without intervening `removed`) — S1 invariant violation, should
  trip `SessionStore[...]:` check() if it ever happens.
- Any STOP-condition.

**Cooldown after E4:**
1. Force-quit both apps.
2. Wait 15 seconds.
